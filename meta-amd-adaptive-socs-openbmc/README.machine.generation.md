# Generating AMD Adaptive SoCs OpenBMC Machines from SDT

This document describes how to generate (or regenerate) Yocto machine
configuration files for AMD Adaptive SoCs OpenBMC boards from System Device
Tree (SDT) artifacts using the `gen-machine-conf` tool.

The `gen-machine-conf` tool converts hardware description data from the System
Device Tree generator (SDTGen) output directory into a Yocto-style machine
configuration. It supports updates if the hardware description changes, and its
output should be used without manual modification.

For more details see:
* [gen-machine-conf Overview](https://edf.docs.amd.com/en/latest/yocto/gen-machine-conf-overview.html)
* [Overview of gen-machine-conf](https://edf.docs.amd.com/en/latest/shel/overview-of-gen-machine-conf.html)
* [gen-machine-conf Best Practices](https://edf.docs.amd.com/en/latest/shel/gen-machine-conf-best-practices.html)

## Generated Files

`gen-machine-conf` owns the following files in the layer `conf` directory. They
are overwritten on each run, so do not edit them manually:

```
conf/
├── dts/<machine>/                      # Generated DTS/DTSI and PL overlay files
├── machine/<machine>.conf              # Machine configuration
├── machine/include/<machine>/          # Generated machine include files
└── multiconfig/<machine>-*.conf        # Generated multiconfig files (FSBL, PMU, etc.)
```

The following files are maintained by hand and are not generated:

```
conf/
├── layer.conf
├── machineyaml/<machine>.yaml          # gen-machine-conf template (input)
└── templates/default/                  # bblayers.conf.sample, local.conf.sample, conf-notes.txt
files/
└── wic/<machine>-sd-efi.wks            # WIC layout file
```

## Prerequisites

1. Complete steps 1 through 5 of [README.building.md](README.building.md) so
   that the sources are synced and an OpenBMC build environment is initialized.
```
$ cd sources/openbmc
$ . setup zcu106-openbmc
```

2. Add `gen-machine-conf` to your `PATH`. It is fetched by the manifest into
   `sources/meta-xilinx/meta-xilinx-core/gen-machine-conf`.
```
$ export PATH=<path-to-sources>/meta-xilinx/meta-xilinx-core/gen-machine-conf:$PATH
$ gen-machine-conf --version
```
> **Note:** `gen-machine-conf` requires `lopper` and `kconfig-frontends`
> (`conf`/`mconf`). If they are not in your `PATH`, they are fetched and built
> automatically using BitBake from within the build environment.

3. Obtain the System Device Tree artifacts for your hardware design. This is
   either:
   * a local SDT directory containing `system-top.dts` generated by SDTGen from
     a Vivado design (XSA), or
   * a URL to a prebuilt SDT tarball (for example, the AMD evaluation board SDT
     artifacts referenced by the machineyaml files in
     `meta-amd-adaptive-socs-bsp/conf/machineyaml`).

## Regenerate an Existing Machine Using machineyaml

Each board layer contains a machineyaml template under
`conf/machineyaml/<machine>.yaml`. The OpenBMC machineyaml inherits the
corresponding AMD Adaptive SoCs BSP machineyaml (which provides the SDT URL,
domain files and PL overlay options) and adds the OpenBMC specific overrides.

Example `meta-amd-zcu106-openbmc/conf/machineyaml/zcu106-openbmc.yaml`:
```
inherit:
    ${BSPLAYERDIR_amd-adaptive-socs-bsp}/conf/machineyaml/zynqmp-zcu106-sdt-full.yaml

args:
    - --machine-name zcu106-openbmc

machine:
    pre:
        MACHINE_FEATURES:
            op: '+='
            val: "fpga-overlay efi"
        ...
```

To regenerate the machine configuration files, run `gen-machine-conf` from the
`zcu106-openbmc` build directory with the machineyaml as template and the board
layer `conf` directory as the config directory:
```
$ LAYER=<path-to-openbmc>/meta-amd-adaptive-socs-openbmc/meta-amd-zcu106-openbmc
$ cd <path-to-openbmc>/build/zcu106-openbmc
$ gen-machine-conf --template ${LAYER}/conf/machineyaml/zcu106-openbmc.yaml -c ${LAYER}/conf
```

> **Note:** `gen-machine-conf` writes its intermediate `output` and
> `hw-description` directories to the current working directory. Running it
> from the build directory keeps the board layer free of these files.

Repeat for the other boards by replacing `zcu106` with `zcu102` or `zcu104`.

> **Note:** When none of the tracked inputs (SDT, template YAML, domain files,
> custom DTSI files) have changed, `gen-machine-conf` skips regeneration. Use
> `--force` to regenerate all configuration files from scratch.

To use a different SDT than the one referenced by the inherited BSP
machineyaml, override `--hw-description` in the OpenBMC machineyaml `args`
section:
```
args:
    - --hw-description <path-or-url-to-sdt>
    - --machine-name zcu106-openbmc
```

## Create a New Machine for a Custom Board

For new platforms or custom hardware designs, create a dedicated board layer
following the existing structure used by `meta-amd-zcu106-openbmc`, so that
board specific configuration remains isolated while common functionality stays
in `meta-amd-adaptive-socs-openbmc`.

The steps below follow the same sequence used to add `meta-amd-zcu106-openbmc`
and it is recommended to keep each step as a separate commit:

| Step | Reference commit (zcu106) |
| --- | --- |
| 1. Add the board sub layer | `meta-amd-adaptive-socs-openbmc: Add meta-amd-zcu106-openbmc sub layer` |
| 2. Add the WIC file | `meta-amd-zcu106-openbmc: Add wks file for zcu106 openbmc sd image` |
| 3. Add the machineyaml template | `meta-amd-zcu106-openbmc: Add zcu106-openbmc.yaml template` |
| 4. Generate the machine files | `meta-amd-zcu106-openbmc: Add zcu106-openbmc machine support` |
| 5. Add the default build templates | `meta-amd-zcu106-openbmc: Add default build templates` |

In the examples below replace `<board>` with the name of your board (for
example `myboard`), which results in the layer `meta-amd-<board>-openbmc` and
the machine `<board>-openbmc`.

All steps are run from an initialized OpenBMC build environment (see
[Prerequisites](#prerequisites)):
```
$ cd <path-to-openbmc>
$ . setup zcu106-openbmc
$ cd <path-to-openbmc>/meta-amd-adaptive-socs-openbmc
$ BOARD=<board>
$ LAYER=$(pwd)/meta-amd-${BOARD}-openbmc
```

### Step 1: Add the board sub layer

1. Create the layer using `bitbake-layers create-layer`. Use `--layerid` so the
   layer collection name follows the `amd-<board>-openbmc` convention used by
   the other board layers (by default it is the directory name).
```
$ bitbake-layers create-layer --layerid amd-${BOARD}-openbmc --priority 6 ${LAYER}
```
   This creates the following layout:
```
meta-amd-<board>-openbmc/
├── conf/
│   └── layer.conf
├── COPYING.MIT
├── README
└── recipes-example/
    └── example/
        └── example_0.1.bb
```

2. Remove the `recipes-example` directory and rename `README` to `README.md`.
```
$ rm -rf ${LAYER}/recipes-example
$ mv ${LAYER}/README ${LAYER}/README.md
```
   Update `README.md` to describe your board and list the layer dependencies.
   See `meta-amd-zcu106-openbmc/README.md` for reference.

3. Update the generated `conf/layer.conf`. Add `BBFILE_PATTERN_IGNORE_EMPTY`
   (the layer has no recipes), `LAYERSUMMARY`, `LAYERDESCRIPTION` and the
   `LAYERDEPENDS` required by OpenBMC and the AMD Adaptive SoCs layers.
   `LAYERSERIES_COMPAT` is already set by `bitbake-layers` to the current
   release. The resulting `conf/layer.conf` should look like:
```
# We have a conf and classes directory, add to BBPATH
BBPATH .= ":${LAYERDIR}"

# We have recipes-* directories, add to BBFILES
BBFILES += "${LAYERDIR}/recipes-*/*/*.bb \
            ${LAYERDIR}/recipes-*/*/*.bbappend"

BBFILE_COLLECTIONS += "amd-<board>-openbmc"
BBFILE_PATTERN_amd-<board>-openbmc = "^${LAYERDIR}/"
BBFILE_PRIORITY_amd-<board>-openbmc = "6"

# Currently no files, so set an empty pattern means ignore the error
BBFILE_PATTERN_IGNORE_EMPTY_amd-<board>-openbmc = "1"

LAYERSUMMARY_amd-<board>-openbmc = "AMD <Board> OpenBMC configurations"
LAYERDESCRIPTION_amd-<board>-openbmc = "OpenBMC Board support package layer \
providing machine .conf, machine YAML, and device-tree assets for <Board>"

LAYERDEPENDS_amd-<board>-openbmc = "\
    core \
    phosphor-layer \
    xilinx \
    xilinx-standalone \
    xilinx-standalone-sdt \
    xilinx-microblaze \
    amd-adaptive-socs-openbmc \
    amd-adaptive-socs-bsp \
    "

LAYERSERIES_COMPAT_amd-<board>-openbmc = "wrynose"
```
> **Note:** Drop `amd-adaptive-socs-bsp` from `LAYERDEPENDS` if your machineyaml
> does not inherit a machineyaml from `meta-amd-adaptive-socs-bsp` (see step 3).

> **Note:** A board layer may also be maintained in a separate repository and
> linked into `meta-amd-adaptive-socs-openbmc` as a symlink. The `setup` script
> follows symlinks when looking for machines.

### Step 2: Add the WIC file

The WIC file describes the SD card partition layout and is placed in the
`files/wic` directory of the board layer, named `<board>-openbmc-sd-efi.wks`.

* **Symlink (recommended):** if the board uses the common OpenBMC EFI SD card
  layout (FAT32 ESP partition with `BOOT.BIN`, kernel and EFI loader, plus an
  ext4 root filesystem), create a symlink to the common WIC file.
```
$ mkdir -p ${LAYER}/files/wic
$ cd ${LAYER}/files/wic
$ ln -s ../../../common/files/wic/common-openbmc-sd-efi.wks ${BOARD}-openbmc-sd-efi.wks
$ cd -
```

* **Copy:** if the board needs a custom layout (for example different partition
  sizes, additional partitions or a different boot device), copy the common WIC
  file and modify it.
```
$ mkdir -p ${LAYER}/files/wic
$ cp common/files/wic/common-openbmc-sd-efi.wks ${LAYER}/files/wic/${BOARD}-openbmc-sd-efi.wks
```

### Step 3: Add the machineyaml template

Create `conf/machineyaml/<board>-openbmc.yaml`. This is the `gen-machine-conf`
template that records the SDT artifacts and arguments used to generate the
machine, so the machine can be regenerated later.

* **Option A: Inherit an existing BSP machineyaml.** If your board is based on
  an AMD evaluation board supported by `meta-amd-adaptive-socs-bsp`, inherit
  its machineyaml (which already provides `--hw-description`, `--domain-file`
  and PL overlay options) and add only the OpenBMC specific settings. This is
  how `zcu106-openbmc.yaml` is implemented.
```
inherit:
    ${BSPLAYERDIR_amd-adaptive-socs-bsp}/conf/machineyaml/zynqmp-zcu106-sdt-full.yaml

args:
    - --hw-description <path-or-url-to-sdt>
    - --machine-name <board>-openbmc
```
  The `--hw-description` line is only needed if you want to override the SDT
  referenced by the inherited machineyaml.

* **Option B: Standalone machineyaml.** For a custom hardware design, point
  `--hw-description` directly to your SDT artifacts. This can be a local SDT
  directory containing `system-top.dts` generated by SDTGen, or a URL to an SDT
  tarball. Pass `-g full` (or `-g dfx`) only if the design includes PL, and use
  `--domain-file` to select the Linux domain.
```
args:
    - --hw-description <path-or-url-to-sdt>
    - --machine-name <board>-openbmc
    - -g full
    - --domain-file ${LAYER_PATH_xilinx-standalone-sdt}/conf/domainyaml/zynqmp-linux-only-base.yaml
```

For both options, add the OpenBMC machine settings, setting `WKS_FILE` to the
WIC file added in step 2:
```
machine:
    description: >
        Machine configuration for <Board> (Cortex-A53 Linux plus FSBL and
        MicroBlaze PMU sub-machines), built from system device tree for OpenBMC.
    pre:
        MACHINE_FEATURES:
            comment: |
                By default, gen-machine-conf includes vcu and mali400 machine
                # features for ZynqMP EV devices. This is not needed for OpenBMC
                # and it is safe to remove.
            op: '+='
            val: "fpga-overlay efi"
        # MACHINE_HWCODECS is only required for ZynqMP EV devices
        MACHINE_HWCODECS:
            comment: |
                By default, gen-machine-conf sets libvcu-omxil machine hw codecs
                # for ZynqMP EV devices based on vcu machine features. This is
                # not needed for OpenBMC and it is safe to remove.
            op: '='
            val: ""
        WKS_FILE:
            comment: |
                Use <board>-openbmc-sd-efi.wks as the default WIC file. Users
                # can override it in local.conf if needed.
            op: '?='
            val: "${@bb.utils.contains('COMBINED_FEATURES', 'efi', '<board>-openbmc-sd-efi.wks', 'xilinx-default-sd.wks', d)}"
```

> **Note:** The Mali-400 GPU (`mali400`) and the Video Codec Unit (`vcu`) are
> not required for OpenBMC builds. Based on the device variant,
> `gen-machine-conf` adds the following by default:
>
> | ZynqMP variant | Default `MACHINE_FEATURES` | Default `MACHINE_HWCODECS` | Example board |
> | --- | --- | --- | --- |
> | EG | `mali400` | - | ZCU102 |
> | EV | `mali400 vcu` | `libvcu-omxil` | ZCU104, ZCU106 |
>
> Defining `MACHINE_FEATURES` in the machineyaml replaces these defaults, so
> the generated machine configuration only contains `fpga-overlay efi` and
> `mali400` (EG and EV) and `vcu` (EV) are removed.
>
> Setting `MACHINE_HWCODECS` to an empty value is only required for ZynqMP EV
> devices to remove `libvcu-omxil`. Omit the `MACHINE_HWCODECS` entry for EG
> devices and update the `MACHINE_FEATURES` comment to only mention `mali400`.
> See `meta-amd-zcu102-openbmc/conf/machineyaml/zcu102-openbmc.yaml` for an EG
> device example.

### Step 4: Generate the machine files

Run `gen-machine-conf` from the `zcu106-openbmc` build directory with the
machineyaml as template and the board layer `conf` directory as the config
directory (see [Prerequisites](#prerequisites) for setting up
`gen-machine-conf`). The intermediate `output` and `hw-description` directories
are created in the build directory, not in the board layer.
```
$ cd <path-to-openbmc>/build/zcu106-openbmc
$ gen-machine-conf --template ${LAYER}/conf/machineyaml/${BOARD}-openbmc.yaml -c ${LAYER}/conf
```

This generates the following files in the board layer:
```
conf/
├── dts/<board>-openbmc/
│   ├── cortexa53-linux.dts
│   ├── pl-overlay-full/pl.dtso                 # only with -g full
│   ├── system-top-no-pl.dts
│   ├── <board>-openbmc-cortexa53-fsbl.dts
│   └── <board>-openbmc-microblaze-pmu.dts
├── machine/
│   ├── <board>-openbmc.conf
│   └── include/<board>-openbmc/
│       ├── microblaze.inc
│       ├── <board>-openbmc-cortexa53-fsbl-features.conf
│       ├── <board>-openbmc-cortexa53-fsbl-libxil.conf
│       ├── <board>-openbmc-microblaze-pmu-features.conf
│       └── <board>-openbmc-microblaze-pmu-libxil.conf
└── multiconfig/
    ├── <board>-openbmc-cortexa53-fsbl.conf
    └── <board>-openbmc-microblaze-pmu.conf
```
The list above is for a ZynqMP design; the generated files vary by SoC family
and design.

Alternatively, without a machineyaml, generate the machine directly from the
SDT directory using `parse-sdt`:
```
$ gen-machine-conf parse-sdt --hw-description <System Device Tree Directory> \
      -c ${LAYER}/conf --machine-name ${BOARD}-openbmc
```

### Step 5: Add the default build templates

The OpenBMC `setup` script only lists machines whose layer provides
`conf/templates/default/bblayers.conf.sample` that includes `meta-phosphor`.
Copy the templates from an existing board layer and update them for the new
board.
```
$ cd <path-to-openbmc>/meta-amd-adaptive-socs-openbmc
$ mkdir -p ${LAYER}/conf/templates/default
$ for f in bblayers.conf.sample local.conf.sample conf-notes.txt; do
      sed "s/zcu106/${BOARD}/g" meta-amd-zcu106-openbmc/conf/templates/default/$f \
          > ${LAYER}/conf/templates/default/$f
  done
```
Verify that:
* `bblayers.conf.sample` includes
  `##OEROOT##/meta-amd-adaptive-socs-openbmc/meta-amd-<board>-openbmc` in
  `BBLAYERS`.
* `local.conf.sample` sets `MACHINE ??= "<board>-openbmc"`.
* `conf-notes.txt` lists the `<board>-openbmc` machine.

### Step 6: Build the image

Initialize a build environment for the new machine.
```
$ cd <path-to-openbmc>
$ . setup <board>-openbmc
```

Then continue from step 6 of the
[Build Instructions](README.building.md#build-instructions) in
[README.building.md](README.building.md) to build and boot the OpenBMC image,
replacing `zcu106-openbmc` with `<board>-openbmc`.

## Generate Machine Files Into a Build Directory

If you only need a quick machine configuration in a build directory instead of
a board layer (as described in the EDF documentation), use `-l conf/local.conf`
to write the `local.conf` changes, and set the machine in `conf/local.conf`:
```
$ gen-machine-conf parse-sdt --hw-description <System Device Tree Directory> \
      -c conf -l conf/local.conf --machine-name <Machine_Name>
$ sed -i "/MACHINE ??=/c\MACHINE ??= \"<Machine_Name>\"" conf/local.conf
$ bitbake obmc-phosphor-image
```
